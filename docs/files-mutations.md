# No-overwrite directory creation, single-file copy and duplicate

`cueward files mkdir`, `files copy`, `files duplicate` and `files receipt` implement creation/copy slices of [issue #42](https://github.com/Termdock-dev/cueward/issues/42). Check installed command help before relying on newer source capabilities. Use these commands only for the user's requested creation/copy/duplicate and selected source/destination; a metadata version is an observation, not authorization.

## Observe, then select the destination

All mutations require one absolute `--root`, a new relative destination and `--expected-parent-version` from `files info` on the destination's existing parent. Copy and duplicate additionally require `--expected-version` from the source's FileInfo. Creating a directory changes its parent's revision, so reobserve before another write. These mutations do not create missing parents, follow symlinks, overwrite, merge or auto-rename conflicts.

```bash
cueward files info --root /Users/me/Documents --path .
cueward files mkdir --root /Users/me/Documents --path Reports --expected-parent-version '<observed parent version>'
cueward files info --root /Users/me/Documents --path report.txt
cueward files info --root /Users/me/Documents --path Reports
cueward files copy --root /Users/me/Documents --path report.txt --destination Reports/report.txt --expected-version '<observed source version>' --expected-parent-version '<observed Reports version>'
cueward files receipt --operation-id '<returned operation ID>'
```

`mkdir --path` creates one empty directory with mode 0700, subject to the process umask. `copy --path` selects the source and `--destination` selects a new file within the same root. Copy supports one available regular file, including empty files and hardlinked sources; the destination is an independent file, not a hardlink/clone relationship. Copy rejects source directory trees/packages, Finder aliases, dataless/unknown source availability, special permission bits and compressed sources. All three mutations reject traversal through symlinks. Alias state must be available/false. There is no link-following option in this slice. Destination parents are scoped filesystem directories, without package-ancestry pruning; an explicitly selected path can lie inside a package, but this does not provide bundle-aware management.

`--max-bytes` for copy/duplicate defaults to 67,108,864 and accepts 1..268,435,456 data-fork bytes. The reported size and streamed growth are bounded. Native extended attribute names are limited to 65,536 bytes and aggregate values to 4,194,304 bytes; these are separate fixed metadata budgets. Oversized metadata is rejected during preflight and rechecked during copying. `--timeout-ms` is 1..30,000 (default 10,000), covering preparation, copying, metadata, read-back verification and checkpoint writes in the worker. Parent-side receipt preparation/finalization is outside the worker deadline. Accepted byte budgets do not bound native peak allocation or transient partial metadata under concurrent changes.

## Duplicate one regular file in its existing parent

```bash
cueward files info --root /Users/me/Documents --path Reports/report.txt
cueward files info --root /Users/me/Documents --path Reports
cueward files duplicate --root /Users/me/Documents --path Reports/report.txt --name 'report copy.txt' --expected-version '<observed source version>' --expected-parent-version '<observed Reports version>'
cueward files receipt --operation-id '<returned or announced ID>'
```

Duplicate is a new source capability pending review; check installed command help. `--name` is one exact new filename, not a destination path. The source's existing parent is the destination parent; the core also enforces this invariant for prepared worker requests. Use copy for another directory. There is no automatic Finder-style suffix, normalization, conflict renaming or same-name no-op: an existing destination, including the source itself or a broken link, is a conflict.

Duplicate reuses the supervised single-file copy engine, not a hardlink, clone or native Finder action. It preserves the source and creates an independent regular file, with the same content/hash, permission/mtime/xattr verification, limits, private staging, root/receipt-storage same-filesystem restriction, error/receipt semantics and cancellation behavior described here. Source read access time is not preserved. The selected file can be empty or hardlinked; directories/packages, symlinks/aliases, placeholders/unknown availability, special permission bits and compressed sources remain unsupported. It does not duplicate directory trees, activate Finder, download data or claim full Finder metadata equivalence. No dry-run is provided for single-file copy/duplicate. Directory proposals use the separate read-only [recursive copy plan](files-copy-tree.md), with separate [authorized execution](files-copy-tree-execution.md) pending review.

## Receipt and exit semantics

The external JSON envelope is `{"Ok":{"operation":"mkdir|copy|duplicate|receipt","result":{...}}}`. Preparation/transport/receipt lookup can instead return structured `Err`. Names, paths and diagnostics are external data, escaped without altering decoded strings.

A loaded mutation receipt is not necessarily a successful write. `mkdir`/`copy`/`duplicate` exit nonzero unless status is completed and completion_verified is true, even when the outer JSON is Ok. `receipt` exits zero when saved evidence was loaded, regardless of the saved mutation status. Always inspect:

| Status | Meaning |
| --- | --- |
| `completed` | The requested object and postconditions were verified before the final checkpoint. |
| `not_started` | A known preflight, staging or publication rejection prevented requested destination creation. Private staged content may remain; an existing destination is untouched. |
| `incomplete` | Destination creation is known; a later error/verification/checkpoint failure occurred. A partial or complete-looking destination can remain. |
| `uncertain` | Delivery/creation/completion cannot be established, including a stopped worker or invalid/lost response. Destination can exist even when the last checkpoint says mutation_attempted=false. |

Receipts include staging_path/staging_verified, operation_id, the original request, status/stage/error, mutation_attempted, optional destination_created, before/post FileInfo observations for root/parent/source/destination, the initial destination_created_observation, optional copy verification, completion_verified, receipt_path and provider_coordination. A before/post observation is not a transaction: null means no successful observation, and an earlier checkpoint can predate interruption. Failed/uncertain receipts must not be interpreted as current filesystem state or proof of absence. Provider coordination is `filesystem_only_provider_state_unknown`, not a cloud completion guarantee.

Stages `staging`, `copying` and `staged` describe private preparation; `creating` records the target publication attempt. `mutation_attempted` concerns target publication, not private staging writes. `staging_verified` records completed private preparation, not delivery. On success, `staging_path` normally no longer exists because the object was moved into place. On failure or interruption, that path can retain an empty, partial or fully verified copy, even with status `not_started`. Old receipts without staging fields remain readable.

Copy/duplicate verification includes SHA-256/bytes of streamed source content and independently read-back destination content, equal permissions/mtime, and a matching extended-attribute digest/aggregate value bytes. The final destination path is reopened and read again. After read-back (or the mkdir emptiness check), the parent and destination paths are resolved again without following links, checked against the original descriptors and compared with their pre-verification revisions before completion. Root/parent/source identities and path revisions are rechecked; the directory's own expected creation change is allowed. Source bytes are never edited, moved or removed.

No mutation is automatically retried or rolled back. Do not replay a failed/uncertain copy/duplicate or delete its destination automatically: inspect its saved evidence, any private staging_path and the actual destination, reobserve the actual paths, then obtain any additional user decision needed for cleanup or a new destination. The worker claims each operation once; a second dispatch of the same operation ID is rejected. `files receipt` only reads the saved checkpoint, without resuming, reconciling or re-executing it.

## Metadata and lifecycle

The macOS adapter prepares an empty directory or fully copied/verified file in the private operation directory before publishing it with `renameatx_np(RENAME_EXCL | RENAME_NOFOLLOW_ANY | RENAME_RESOLVE_BENEATH)`. Publication resolves the entire relative destination from the held selected-root descriptor, never from a cached destination-parent descriptor. It does not overwrite existing destinations or traverse symlinks. A parent moved outside root before publication cannot receive content through its stale descriptor. After publication, the worker only observes/reads the published object; it performs no further payload or metadata writes. Other actors can still move or change an already published object, and final checks do not freeze the namespace. The held root anchors the selected directory object, not a permanent absolute pathname or a sandbox against every external operation.

The root and private receipt storage must be on the same filesystem. Different-device roots are rejected before staging source content. A private empty-object capability probe checks required kernel flag enforcement; unsupported kernels/filesystems fail with `unavailable`, without a cached-parent or cross-device copy fallback. This deliberately limits external-volume support rather than weakening publication guards.

The generic core streams and hashes bounded data into private staging; the adapter copies extended attributes with `fcopyfile(COPYFILE_XATTR)` and verifies all enumerated names/values against the source. Ordinary POSIX permission bits and modification time are set and compared before publication. Owner/group, ACLs, birth time, access time, file flags, sparse layout, hardlink relationships and cloud/provider metadata coordination are not preserved/verified by this contract. ACL inheritance comes from private staging, not the destination parent. Setuid/setgid/sticky sources and compressed sources are excluded rather than copied with uncertain security/compression semantics. Metadata precision/support differences can reject staging without creating a destination. Final read-back failure after publication instead leaves an incomplete outcome.

Receipts live in mode-0700 operation directories at `~/.cueward/operations/files/<operation-id>/receipt.json`; receipt/claim files are mode 0600. The parent prepares a receipt before dispatch. Private staged-object data can remain alongside receipts indefinitely after failure or interruption, subject to the copy data/xattr budgets; the operation directory stays private even when the staged file receives source permissions. There is no automatic staging cleanup or expiry. The worker syncs and atomically replaces checkpoints before staging/publication and at later stages; the parent checks the returned receipt against stored evidence. Before dispatch, the parent flushes a generated `operation_id` and a `files receipt --operation-id` command to stderr; the final external JSON on stdout is unchanged. Save this progress line to retrieve evidence if the CLI is interrupted. Failure to publish it prevents worker dispatch.

Mutation workers use a parent-owned stdin socket for newline-framed input and lifetime monitoring. EOF, transport failure or unexpected subsequent input stops the entire worker; parent SIGINT, SIGTERM and SIGKILL close this lifeline even though the worker has its own process group. A dead parent before worker startup is rejected before mutation. No process-global signal handler or PID polling is used. A timeout still stops the owned process group and records uncertain. Parent interruption cannot return a final response or finalize the receipt, so use the announced ID to read the last saved checkpoint. Termination is not rollback: private staging can remain, and submitted publication/provider work can leave a destination. Older receipts can describe partial destinations from earlier versions. A previously verified final checkpoint can remain completed if the operation finished before interruption. There is no automatic evidence expiry, partial-file deletion or rollback. These checkpoints support process interruption, not a power-loss durability guarantee or an atomic multi-object filesystem transaction.

The filesystem worker denies dataless materialization and never calls a download API. It does not coordinate generic provider services or prove cloud synchronization. Paths/versions detect observed changes, not malicious concurrent swaps or every server-side operation after worker termination. Parent relocation/replacement observed during final verification prevents completed status even if the reopened descriptor remains readable and the selected root is unchanged. Checks are observations, not an atomic path lock; changes after the final checks are still possible. Network/provider/volume/TCC errors remain errors or uncertain outcomes, not verified empty content.

## Acceptance and remaining work

Disposable tests cover content/hash/readability, empty files, hardlinked sources, Unicode/newline/external-marker paths, permissions/mtime/native xattrs, existing/broken-link conflicts, late conflicts, stale source/parent revisions, path scope, source directories/packages/links/aliases, metadata budgets, permission denial, post-copy source change, outside-root parent relocation or symlink replacement at publication, no post-publication payload writes after external relocation, unsupported publication flags, different-device refusal, backward-readable receipts, nested-parent relocation/directory or symlink replacement after reopening the final read-back descriptor, checkpoint failure, stopped-worker uncertainty, delayed-start and armed-worker parent SIGINT/SIGTERM/SIGKILL interruption, pre-dispatch operation ID publication, private saved receipts and rejected replay. Duplicate-specific checks also cover sibling-only worker input, exact new names, independent edits, old/new action serialization, existing/late conflicts and delayed/armed parent interruption. They do not mutate personal files.

Cross-volume publication is unsupported and explicitly rejected. True read-only/unmounted volumes, real File Provider/TCC behavior, ACL inheritance and older macOS remain unverified. Tag observations, atomic initial tagging and no-op checks (not existing-tag edits) use the separate [file tags contract](files-tags.md). Same-volume rename/move use the separate [file relocation contract](files-relocation.md). Ordinary tree copy has a separate [execution contract](files-copy-tree-execution.md) pending review. Package duplication, trash/recovery and cross-volume operations remain subsequent #42 work. Batch planning and independent execution use the separate [batch contract](files-batch-execution.md). Permanent deletion is not included.

Native reference: Apple's [copyfile implementation/manpage](https://github.com/apple-oss-distributions/copyfile/blob/main/copyfile.3) distinguishes data, xattr and other metadata flags. The Darwin declarations/constants were checked against the local macOS SDK; this slice requests only COPYFILE_XATTR, not full Finder copy equivalence.

Guarded publication reference: Apple’s [XNU rename implementation](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/vfs/vfs_syscalls.c) and [path resolution](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/vfs/vfs_lookup.c) define the no-follow/beneath behavior. Constants were checked against the local macOS 27 SDK; runtime probing, not that SDK version alone, gates availability.
